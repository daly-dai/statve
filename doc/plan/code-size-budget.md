# doc/plan/code-size-budget —— 代码体量预算：前端组件 ≤ 500 行（C64）

> 池子行原文照搬（2026-11-18 用户定）：
> **前端组件不能超过 500 行，超过 500 行必须要拆分。**

**定位**：长期项。不是一次性重构，是**给"文件会长胖"装一个判据** —— 所以它的重点不是"把 `page.tsx` 拆了"，而是"以后不许再长回来"。

---

## 一、需求（人话）

组件太长了读不动：一个文件里塞着状态、副作用、十几个 handler 和四块 JSX，改任何一处都要先翻 700 行。用户定的红线是 **500 行**。

**AGENTS.md 第 11.9 条已经有这条原则**（「页面超过 500 行 → 拆组件」），而且写得比"500"细：

- 500 是**触发线不是目标**：不到 500 行但"一个文件里两件事"就该拆
- 超过 500 行但逻辑单一（如一个长 switch）可以留
- 怎么切：按「**能一句话说清它负责什么**」

⇒ 本项要补的是**机器判据**（跑一下就报），不是重新发明原则。

## 二、现状（先统一"行数"的口径，否则同一天能数出两个数）

⚠️ **口径问题真的存在**：同一个 `app/page.tsx`，用 `split("\n").length` 数是 **722**，用 `Measure-Object -Line` 数同一份内容（`git show HEAD:app/page.tsx`）是 **680**。差的是空行怎么算。
`AGENTS.md` 的「环境与验证」里已经记过同族的坑（`Get-Content` 数行数给出假数字）。

**本文件的口径 = 物理行 = `text.split("\n").length`**（也是编辑器显示的那个行号）。脚本按这个数，人工核对也按这个数。

## 三、详细设计（判据与脚本）

| 项 | 定案 |
|---|---|
| 度量 | **物理行**（`split("\n").length`），从文件第一行到最后一行的行数，含注释与空行 |
| 阈值 | **500**（用户定，不讨论） |
| 范围 | `app/**/*.tsx` —— **包括 `page.tsx` 这类路由文件**（它就是典型违规者） |
| 排除 | `*.test.tsx`（测试本来就长且碎，行数不是它的可读性指标）· `app/components/ui/icons/index.tsx`（C63 落地后会是一堆数据表，行数无意义 —— **这条等 C63 动工时一起加进排除表**） |
| 不纳入 | `.module.css`（最大 457）与 `app/lib/**` 纯函数（最大 393）：**一次只上一把尺**，两条各立观察线，等它们真超了再说 |
| 落点 | `scripts/check-size.mjs`：列出所有超阈值文件 + `process.exitCode = 1`；与 `scripts/check-plan.mjs`、`scripts/check-feedback-tokens.mjs` 同一族（**跑一下就报**，不靠记性） |
| 调用方式 | 先 `pnpm size`（手动）+ 每个功能收尾必跑；**暂不进 husky 钩子** —— 理由同 C63：先把判据做出来，等"又写超了"真的发生一次再升级成拦截 |

**脚本形状（不到 40 行，纯 node，无依赖）**：

```
node scripts/check-size.mjs
  → 扫 app/**/*.tsx（跳过 *.test.tsx 与排除表）
  → 按行数降序打印前 10
  → 超 500 的单独列一节，红字，退出码 1
  → 全绿时打印一行「最大 458（app/repos/page.tsx）」——有读数才看得出趋势
```

## 四、拆分路线（`app/page.tsx` 的四刀，按"能一句话说清"切）

现在 `Home()` 本体约 560 行（76–636），后面还挂着 6 个模块级纯函数（637–722）。

| # | 拆出 | 一句话职责 | 估计移走 |
|---|---|---|---|
| 1 | `app/components/composer/` | 输入台：卡 + textarea + 工具栏 + 状态条 + 空态工作空间行 + 命令面板接线 | ~180 行（含 `composerPlaceholder`） |
| 2 | `app/components/empty-hero/` | 新会话空态的品牌与提示（现在是模块级 `emptyHero()`） | ~30 行 |
| 3 | `app/components/session-head/` | 右栏第一行：标题 + 模型名 + 「对话/轨迹」tab | ~60 行 |
| 4 | 剩下的 `Home` | 状态与编排：session / runs / traces 三条线 | —— |

**四条硬约束**：

1. **输入框不许重挂**（C57 的 4.13 第 1 条）：`Composer` 在 `Home` 里是**稳定子节点**，空态 ↔ 会话态只换 props / `data-*`，不换组件身份。
2. **拆出来的组件通过 props 收数据、不读全局 store**（§10.9 第 4 条）。若某个组件要读三个以上的 store，说明切口选错了。
3. **一行逻辑不搬家**：这一批是**纯搬迁**，不改行为。撞到需要改逻辑的地方，单独开一行池子，别混进来。
4. **拆完仍超 500**：第 5 刀是 `app/lib/use-session-actions`（新建 / 重命名 / 删除 / 选择这一组互相牵动的 handler）。⚠️ 但要先判断它是不是**纯计算** —— 不含 React 状态与副作用的东西**不许包成 hook**，该进 `app/lib/`（§11.9 的核心分界）。

**顺序**：先 2（最小、最独立）→ 3 → 1（最大，但约束最硬）→ 再量一次，决定要不要第 5 刀。每步 `tsc` 绿再下一步。

## 五、验收

1. `node scripts/check-size.mjs` **退出码 0**、违规 0；输出里能看到「最大 …」那一行读数。
2. `app/page.tsx` **≤ 500**（物理行）；`app/repos/page.tsx` 458 不动它（没超就不许顺手改）。
3. **行为不变**：`tsc` 0 / `eslint` 0 / 全量单测绿；真机四种状态各点一遍（空态 · 对话 · 审批弹框中 · 长回答滚动），**输入框不重挂**（打半句 → 切到空会话再切回 → 字还在，且不触发新的 run）。
4. 拆出的每个组件都能用一句话说清职责（写进组件文件头注释）；任何一个说不清的，就是切错了。
5. 红线文件 `lib/agent/index.ts` **零改动**（本项全在 `app/`）。

## 六、⚠️ 缺什么才能定案（三个待拍板）

1. **`.module.css` 与 `app/lib/**` 要不要一起上尺**？建议**先只 `.tsx`** —— 一次只上一把尺，三条尺同时上会把"代码优化"变成"到处重构"。
2. **C63 的 `ui/icons/index.tsx` 要不要提前进排除表**？建议**等 C63 落地时一起加**（现在那文件还不存在，不加空规则）。
3. **脚本挂在哪**：`pnpm size` 手动 / 收尾必跑 / husky 钩子拦截？建议**手动 + 收尾必跑**，被咬一次再升级。

## 七、施工顺序（定案后）

1. 先写 `scripts/check-size.mjs` 并**让它红**（现在 `page.tsx` 722 ⇒ 退出码 1）—— 这就是这条规则的"先红"
2. 拆 2 → 3 → 1，每步 `tsc` 绿
3. 跑绿：脚本 0 + 单测绿 + 真机四状态
4. 收尾：补 `doc/weekly-review/*/00-过程日志.md`、池子改 `已交付`

### 8.2 三条硬约束的落地情况

1. **输入框不重挂**：`<Composer>` 在 `Home` 里是**无条件**子节点（`<div className={styles.composerArea}>` 里），
   空态 ↔ 对话态只换 props。切 tab / 等审批卡 / 切会话，文本区不重建。
2. **不碰别人的 store**：四个新组件全是 props 收数据。`<Composer>` 连"有没有会话"都不问 —— 它只收 `state.disabled`。
3. **一行逻辑不搬家**：唯一"语义上动过"的地方记在 8.3 ②。

### 8.3 拆的时候真撞上的四个坑（都是下一个拆的人会再撞的）

1. **CSS Modules 让"跨文件的类名"根本指不到。** `page.module.css` 原来有
   `.stage[data-empty] > .composerArea` / `> .transcript` 这类**从祖先类选择后代类**的规则；后代搬走之后，
   那个类名在新文件里被哈希成另一个名字，规则静默失效（不报错、只是布局不对）。
   ⇒ 解法只有一条：**跨组件边界的钩子改用属性选择器**（`[data-role="transcript"]`、`[data-empty]`），
   属性不受哈希影响。这条已经写进 `page.module.css` 的头部注释，谁再拆都会先看到。
2. **"谁在栅格里哪一行"必须留在页面。** `.stage` 的行模板、`.composerArea` / `.decisionHost` 的 `align-self`
   都是**舞台的规则**，不是组件自己的样子。拆的时候容易顺手把 `.composerArea` 一起搬进 composer —— 搬完就发现
   页面的 `data-empty` 规则没东西可选中了。判据一句话：**这条规则是在管"它在页面上的位置"还是"它自己长什么样"**。
3. **布局 effect 的依赖要换对。** 吸底滚动的 effect 原来盯 `[messages, follow]`；搬进 `TranscriptPane` 之后它拿到的是
   折好的 `turns`（`buildTranscript(messages)` 的产物，`useMemo` 缓存）。**引用变了就等于"有新内容"**，
   所以依赖改成 `[turns, follow]` 是等价的 —— 但这一条要能说出"为什么等价"，不然就是搬错了还看不出来。
4. **死 CSS 会被搬走而不被发现。** `.modeBar`（审批模式切换条）在 C57 把档位搬进输入台卡片之后就没人用了，
   但因为它住在 `page.module.css`，一直没人注意。这次搬样式时靠"声明级对账"（见 8.4）才捞出来，顺手删了 15 行。

### 8.4 怎么证明"是搬家不是改写"（这一节是可以复用的方法）

| 关 | 做法 | 结果 |
|---|---|---|
| 样式 | 取 `git show main:app/page.module.css` 的全部 `prop: value` 声明，和新 5 个文件的并集做集合差 | 旧 125 → 新 123；"旧有新无"只有 `.modeBar` 那 2 条；"新有旧无" **0 条**（没发明任何值） |
| 接线 | 每个 `.tsx` 里的 `styles.X` 引用集合 vs 自己的 `index.module.css` 定义集合，双向查 | 缺失 0、**死样式 0** |
| 产物 | 起 dev server，抓 SSR HTML 里的 class 哈希 | 四个新组件的哈希**各不相同**，且分别来自各自的模块（证明样式没接错文件） |
| 编译后 | 抓 CSS chunk 反查被搬走的关键规则（`scrollbar-gutter` / `visibility:hidden` / `--col` / `34px` 圆 …） | 全部命中 |
